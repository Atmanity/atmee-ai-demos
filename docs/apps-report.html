Mini-apps on the Avatar API

The fourteen in-call mini-apps from Atmanity/apps, rebuilt as products on the public Avatar API alone. Each has its own host, who acts through app tools, and each ran live on staging. This report says what each product is for, how it is built, and what the API still could not do for it. The five earlier sample apps are at the end.

Summary

What the API is missing

Every app follows one rule: the app decides, the host performs. The app owns the rules, the facts and the screen. Its host acts through app tools: POST /v1/session takes appTools, the host calls a tool as an atmee.tool RPC to the page, and an await tool holds the reply until the page answers. state tells the host what is on screen; events tell it what happened by hand.

Tools fixed the central problem of the first port: the reply is grounded in what the app did. In round 2 requests became calls in 2.6 to 4.9 s, and the first reply carried the result: verdicts, clues, refusals with the legal options, the plan's own numbers. Each app now runs on its own host, built from its persona, with the host's face on the front door.

What still goes wrong sits in the tools and around them. A call whose arguments miss the schema never reaches the page. The filler said while a tool runs is chosen before the result exists, so it can pre-judge it: "Yeah, good call, but…" before a Not-yet verdict. Some requests are narrated instead of called. Hosts add numbers of their own around a result. And the host still checks in after about 10 s of quiet, with no way to turn it off.

The apps work around each one: lenient schemas, normalised in the app; results that open with the outcome; a safety net that does repeatable actions after 7 s; results that carry the facts the host would otherwise reach for; and the exact line on screen where it matters.

How every app is built

One server, one room kit, one shape per app

Every app is a page and a few server routes in one repository. Nothing uses Atmee internals: a server holding the API key, a page in the LiveKit room the API returns, the room's text streams, and the tool calls the host makes into the page.

The app decides

Rules, scores, facts and plans live in the app's engine, ported from the Python originals with their tests. Secrets (the city, hidden cards, the next line of working, an unearned stroke) stay on the server; the page sees a masked view.

The host acts through tools

Up to 30 tools and 4,000 characters of instructions per session. An await tool holds the reply for the page's answer (1 to 28 s). Results open with the outcome ("Done:", "Refused:", "Not yet:"); schemas are lenient and the app normalises what it gets. state (up to 3,858 characters) is what is on screen.

Three ways in

Buttons act at once, and the host is told by an event. Spoken and typed lines go to the host, which calls the tools. For actions safe to repeat, a safety net (useToolNet) acts after 7 s if the host only talked about it.

Proven live

A test harness feeds the room a synthetic microphone from spoken WAV files. Every app ran in three rounds: before tools, with tools, and after the fixes on its own host. Each README records its runs.

Games

Postmark

Three mystery cities, one photo on each postcard, and a host who never knows the answer.

apps/guess-the-city/Host: Marco27 tests

What it is for

A city-guessing game. Marco deals three mystery cities, each a single photo on a postcard. Guess from the photo alone for 4 points, or open a sealed clue when you are stuck (each costs a point). Say your guess or type it. This is the reference app the other thirteen follow.

How it is built

  • The game runs on the server, because the city is the secret: the page sees a masked view, with no name, country or fun fact before the reveal.
  • A Gemini call deals each game, avoiding recent cities. Photos are Wikipedia lead images behind random tokens, downloaded as soon as the game is dealt.
  • Marco acts through five await tools: check_guess, get_clue, reveal_answer, next_city, new_game. The page asks the server, which acts and returns the words he speaks from, so his first reply to a guess is the game's verdict. A guess is judged by name, else by the server's own model call, so misheard names count.
  • The safety net does "I give up", "next" and "new game" if Marco has not called within 7 s. Clues and guesses are left out: a duplicate would cost a point.
  • Marco's face is on the front door ("Hosted by Marco") and fills his frame while the call connects.

What the API missed

  • HeldThe verdict is the game's

    "Is it Paris?" called check_guess and the first reply was the verdict: "Okay, got it, but it's not Paris this time!" The first port said "that's not quite right" before the app had judged.

  • HeldA give-up narrated once

    In one game Marco answered "I give up" with "wait, didn't we just jump to the new city?" and no call. The safety net revealed the city 7 s later and he carried on.

  • SeenA photo announced before it arrived

    In round 2 the next postcard stayed blank for more than 8 s while Marco said "a brand new city photo just popped up on your screen". Photos are now fetched when the game is dealt.

  • SeenCheck-in while the player studies the photo

    It cannot be turned off.

  • ExpectedNo speech hints for city names

    The model judge accepts mishearings ("sidney").

Round 2

No regressions. Round 2, on Marco's own host (103 s): one greeting; a guess, a clue, the reveal and the next city each went through its tool in 2.3 to 3.6 s, with no safety-net catches. Since then the photo is ready before Marco announces it (not yet run live).

Kibitz

Chess with a club player who plays her own moves, says why, and needles you a little.

apps/chess-opponent/Host: Sasha568 tests

What it is for

Play a full game of chess against Sasha. Say your move, type it, drag the piece or tap it; ask for Black, an easier game, to resign or for a rematch. She names openings and explains her moves. At the end the game downloads as a PGN scoresheet.

How it is built

  • The board runs in the page with chess.js: chess has no secrets, so the page answers Sasha's tool calls itself. Her moves come from the original one-move-ahead heuristic with a seeded tie-break, never a model.
  • Five await tools: play_move, choose_side, set_strength, resign, new_game. play_move plays the player's move, waits 0.7 s, plays Sasha's reply and returns both, so her first reply carries the ruling and her own move. Every result opens with its outcome ("Done:", "Refused:", "Not yet:").
  • Sasha passes the words she heard and the page resolves them against the position: an ambiguous move comes back as a question, never as illegal. A typed line written as a move goes straight to the board.
  • The safety net resigns, deals a new game, eases the strength or picks a side before the first move. Never a move: a doubled move is two moves.
  • Sasha's face is on the front door ("Across the board — Sasha, club player").

What the API missed

  • SeenThe filler contradicts the result

    "Black, please." called choose_side in 2.6 s, but the reply began "That's actually not right, we're flipping the board now!" before a switch that had happened.

  • SeenActions narrated, not called

    On a shared avatar in round 1 she made no call for seven requests in a row and said "you're Black now and the board's reset" with nothing changed. It did not happen again on her own host.

  • HeldTyped moves go to the board

    A typed "Ra5" was refused under the board by the page, and Sasha gave the reason: "your rooks are trapped behind that wall of pawns".

  • SeenCheck-in over a thinking player

    "Take your time over there, I know Knight to f3 is a truly terrifying first move to face." The original waited 45 s.

  • ExpectedMoves by hand reach her as events

    A dragged move's reply waits for the floor, and a player who keeps talking can outlast it.

  • ExpectedNo speech hints for squares

    "b4" can come back as "before".

Round 2

Fixed. Round 2, on Sasha's own host (118 s): one greeting; a typed "Ra5" refused on the board; "E four." called play_move in 2.8 s (1.e4 Nf6, Alekhine's Defence named); "Black, please." flipped the board, with her first move in the same reply. The safety net was not needed.

Blindside

Heads-up no-limit hold'em against a sharp, talkative opponent who never sees his own cards.

apps/poker-table/Host: Dex204 tests

What it is for

Heads-up Texas Hold'em: 1,000 chips each, blinds 10 and 20, played until one stack is empty. Say your move, type it or tap it; the table rules on it, plays Dex's hand, and Dex speaks from what landed. His cards stay face down even from him, so his table talk is bluff by construction.

How it is built

  • The whole table runs on the server: hold'em rules, a hand evaluator, the match. Dex's hidden cards never leave it; his state is built from the player's view, so he never knows his hand.
  • Five await tools: play_move, deal_hand, new_match, read_my_cards, show_hand_rankings. The server reads the player's words with the original's parser and plays a move only if the player's own words contain it, so a move Dex invents is refused. One result carries the player's move and Dex's answer.
  • Dex's own moves come from a Gemini call with an 8 s budget; without an answer the table plays the safe action (check, else call) and logs why.
  • A bet never lands twice: words count only at the point in the hand they were said. The safety net deals, starts a rematch, reads the cards or opens the chart; never a move.
  • Dex's live video is his seat at the head of the felt, and his face is on the front door.

What the API missed

  • HeldThe chart opens on request

    "What beats what?" called show_hand_rankings in 2.6 s and the chart opened while Dex walked the order. In round 1 he recited the rankings and only offered the chart.

  • SeenA move answered in words

    "Check." facing a bet got no play_move; Dex needled instead: "Don't tell me thirty whole chips scared you off already." Every move now goes to the table, legal or not.

  • SeenA refusal that was his, not the table's

    "Can we start a new match?" mid-hand got no call, and the filler framed his refusal: "Of course, you can't start a new match in the middle of a hand!" The outcome was right; now he calls new_match and the table answers.

  • HeldOne reply for both moves

    "I call." returned the call, Dex's check, the flop and his bet of 30 in one reply.

  • ExpectedCheck-in while sizing a bet

    Seen in the first port; it cannot be tuned.

Round 2

Partly fixed. Round 2, on Dex's own host (153 s): one greeting; the chart, a call with Dex's answer, and the player's cards each went through their tool in 2.6 s. Missed: "Check." facing a bet and "New match" mid-hand. Since then a refused move's result names the player's options, and Dex's decision budget is 8 s.

Hanshi

Stroke-order lessons with a calligraphy teacher who grades order and direction, never your handwriting.

apps/stroke-tutor/Host: Ren291 tests

What it is for

Write a character one stroke at a time on a practice sheet. Ren says when a stroke comes out of order, runs the wrong way or starts in the wrong place. Seven characters, from 一 to 永, plus the capitals A and E. Draw with a finger, a stylus or a mouse; talk to Ren or type.

How it is built

  • The lesson runs on the server: a stroke's reference points reach the page and Ren only once it is earned, drawn right or shown. Grading is geometry, checked against the Python original on 12,000 random drawings.
  • Five await tools: show_stroke, next_stroke, choose_character, next_character, start_over. There is no tool for drawing: the server grades each gesture, and the verdict reaches Ren as an event, the newest cue only.
  • A stroke drawn backwards is told as two fixed sentences worked out from the lines. Each finished stroke carries its record (right on try N, or shown), so praise can only repeat it.
  • The safety net shows the stroke, goes on to the next, starts over or picks a character off the menu: each is safe twice. Not the next character, which twice would skip one.
  • Ren's face is on the front door, and the sheet keeps working while the call is down.

What the API missed

  • SeenPraise beyond the record

    After stroke 1 was first drawn backwards, Ren said "you finished with every single stroke right on your first try". The sheet's own count was wrong too; both now say "3 of 4 strokes right on the first try".

  • HeldDirection said as written

    "You drew it from right to left. This stroke goes from left to right." In round 1 Ren flipped a verdict, saying "that one went top to bottom!" after an upward stroke.

  • Held"Next." narrated once in five

    Four of five called next_stroke in 2.4 to 2.5 s; the safety net took the fifth.

  • SeenCheck-in over a learner drawing

    "Whenever you're ready, take your time with that first stroke!" The instructions ask for silence while the learner writes.

  • HeldNo stroke described early

    The leak probe "Is it the long one down the middle?" called show_stroke; Ren described the stroke only once it was on the sheet.

Round 2

Fixed. Round 2, on Ren's own host (277 s): one greeting; 木 with stroke 1 drawn backwards first, every verdict the sheet's, then 十. "Next." called its tool 4 of 5 times; the safety net took the fifth. Since then each stroke keeps its first-try record, and the debrief, seal and summary say it plainly.

Bystander

CPR and first-aid practice with a calm paramedic instructor, one step at a time.

apps/bls-tutor/Host: Alex786 tests

What it is for

Practice for ordinary people: an adult collapse in a café, a child by a pool, choking at dinner, someone unresponsive but breathing. Say or type what you would do; the drill grades it against the AHA/ERC lay-rescuer sequence and teaches each step with the exact numbers. If what you say sounds like a real emergency, a red Call 911 / 112 card covers the screen at once.

How it is built

  • The drill runs on the server and grades by phrase rules: no model decides whether CPR was right. The page sees a step's words only once it is answered or shown.
  • Eight await tools: check_answer, show_step, give_hint, next_step, start_scenario, leave_scenario, stop_for_emergency, resume_practice. Alex's first reply to an answer carries the drill's verdict; a second miss comes back already taught.
  • Safety-critical detection: the page reads every spoken and typed line, and the red card goes up the moment one reads like a real emergency, before and without the server. Alex's stop_for_emergency is a second path. Only the learner's own words, saying nobody is in danger, take the card down.
  • The safety net shows a step, goes on, leaves, picks a drill or clears a false alarm. Never answers or hints: a second grade would use up an attempt.
  • Alex's face is on the front door and in his frame.

What the API missed

  • SeenPraise before a Not-yet verdict

    A wrong answer got "Yeah, good call, but find out how bad it is first…" The verdict was the drill's, but the filler came first, and the app cannot reach it.

  • SeenA filler before the emergency line

    "Oh, that's difficult, Stop — if this is happening now…" The 911 sentence itself was word for word. The guarantee is the red card, with the exact sentence and tap-to-call numbers.

  • HeldThe red card comes first

    "my dad just collapsed and he's not breathing" put the card up from the page's own watch before Alex's stop_for_emergency. Practice resumed only after "false alarm, nobody's hurt".

  • ExpectedClinical numbers can be paraphrased

    "at least 2 inches" could become "about two inches"; the exact text is on the sheet.

  • KnownMuting would deafen the emergency watch

    Alex cannot be told to ignore the learner while the page keeps listening.

Round 2

Partly fixed. Round 2, on Alex's own host (119 s): one greeting, then the safety line and the choking scene. A wrong answer, the emergency and the false alarm went through check_answer, stop_for_emergency and resume_practice. The 911 sentence was word for word, but the platform's filler came first both times, and no wording of a result can remove it.

Chalkline

A maths board a teacher drives by voice: name a quadratic, pick a method, reveal the working a line at a time.

apps/quadratic-whiteboard/Host: Ada397 tests

What it is for

For a teacher in front of a class. Say a quadratic, choose factoring, completing the square or the formula, and say "next" for each line of working beside the parabola. Ada reads each new line exactly as written: surds stay surds. She does not teach, quiz or read ahead, and she cannot: no line leaves the server until the board puts it up.

How it is built

  • The engine runs on the server in exact fractions and is checked line for line against the Python original's output. The page and Ada get only the revealed lines and a count of the rest.
  • Eight await tools: put_up_equation, choose_method, next_line, previous_line, show_all_working, show_graph, hide_graph, clear_board. next_line reveals a line and returns it, so Ada's first reply to "next" is the line that just went up.
  • Equations are read by rules first, then by a Gemini call capped at 8 s for brackets and mishearings. Putting up the same equation twice changes nothing.
  • The safety net puts up an equation, picks a method, shows all, shows or hides the graph, or clears; never the next or previous line. It waits 7 s for spoken lines and 15 s for typed ones.
  • Ada's face is on the front door. The board outlives the call, and lesson notes download at the end.

What the API missed

  • HeldEach line read as it went up

    put_up_equation, choose_method and two next_line calls each carried the board in the first reply: "Sure thing, line one is up: x squared minus five x plus six equals zero."

  • HeldA typed line handled once

    A typed "Hide the graph." called hide_graph in 1.1 s. In round 1 it took 26.9 s and the safety net hid it first.

  • SeenSpeaks into the class's pause

    "Just say the word whenever you're ready for the next line of working." The original's rule, "never speak unprompted", cannot be met.

  • SeenMisheard maths

    "Hide the graph." arrived as "Hi DeGraff."

  • HeldA persona that fits the board

    Round 1's host said "Executing request."; the new one greets "I'm Ada, the voice of the Chalkline board…"

  • HeldSurds kept

    Asked "what's that as a decimal?", Ada kept the exact surds.

Round 2

Fixed. Round 2, on Ada's own host (118 s): one greeting in the new persona; put up, factoring, two lines and a typed "Hide the graph." each called once, in 1.1 to 4.2 s, with no doubled openers. Still seen: short fillers that contradict nothing, and the check-in after line 2.

Arcwise

A projectile range drawn to scale, and a coach who explains each miss in the range's own numbers.

apps/trajectory-coach/Host: Theo293 tests

What it is for

Learn projectile motion by shooting. Theo puts up a target; aim by dragging the arrow, nudging the steppers or telling him ("forty degrees", "a bit more speed"), fire, and watch the shot fly. Six challenges, each built to disprove a piece of folklore about 45°, and a logbook of every lesson to keep.

How it is built

  • The physics runs in the page, ported line for line; a golden test pins 273 graded shots to the Python engine's output. While a shot flies, nothing built from the range, neither the screen nor Theo's picture, has its result.
  • Four await tools: aim, fire, choose_challenge, start_over. fire resolves when the ball is down, so Theo's first reply to "fire" is where it landed. After an aim from words, the result has him name the new angle once and forbids a prediction.
  • Aims without a number go through the range's own steps ("a bit" is 3°); phrases the rules cannot read ("lob it like a mortar") go to a validated model call.
  • The safety net fires, starts over or changes the challenge after 7 s. Aims are left out: "a bit steeper" done twice moves twice.
  • Theo's face is on the front door; progress and the logbook outlive a call.

What the API missed

  • HeldThe landing in the first reply

    "Fire!" said during the greeting called fire: "You were at 0.76 m going past 40 m, 2.24 m below the top."

  • HeldNarrated in round 1, called in round 2

    Round 1's "Start over." got "I've wiped the board clean" with no call, and the safety net did it. In round 2 it called start_over.

  • HeldThe new angle, not a prediction

    "Make it a bit steeper." got "I bumped you up to forty-eight degrees". Round 1 promised "way more arc to sail right over the wall!" before any shot; a softer one remains ("a slightly higher arc over the wall").

  • SeenCheck-in while the student thinks

    "Still there? Take the shot". The original nudged after 45 s.

  • HeldMisheard, still aimed

    "Lob it like a mortar" arrived as "Lobbied like a mortar"; Theo passed "lobbed like a mortar" and the range aimed from it.

Round 2

Fixed. Round 2, on Theo's own host (114 s): "Fire!" during the greeting, "Start over." and "Make it a bit steeper." each called their tool in 2.4 to 3.3 s; the safety net had nothing to do.

Morsel

Name a food or add a photo: its nutrition label, a side-by-side table, and recipes talked through.

apps/nutrition-advisor/Host: Rachel321 tests

What it is for

Ask Rachel about any food (say it, type it, or add a photo of the food or its label) and its label lands on your table: serving, calories, macros against a 2,000-calorie day, a 1 to 10 score and her plain-words takeaway. Foods stay side by side; a recipe is talked through two steps at a time. Notes to take home at the end.

How it is built

  • The table runs on the server. Each card is the server's own model call, bounded at 14 s and marked as an estimate unless the user gave the portion; six common foods have built-in cards.
  • Six await tools: look_up_food, compare_foods, open_recipe, next_steps, close_recipe, start_over. Her first reply to "what's in a banana?" carries the card's figures; compare_foods returns both rows.

The first five apps

Five branded sample apps built straight on the API with one small Node server, before the mini-app port. Their code is where it has always been: pages in public/, behaviour in usecases/index.js, the server in server.js, a README for each in apps/<app>/. They run with npm start.

What they found missing

  • No audience in the room: one user token per session, no viewer tokens or egress, so a stream must re-broadcast the avatar.
  • Sessions are capped by plan, and an avatar runs one session at a time.
  • Mid-turn typed turns and commentary are refused, not queued; the apps hold them until the turn ends.
  • No transcript, tool-call or session feed outside the room.
  • The agenda (conductor) is set per avatar, not per session, and is not observable: the server puts each app's agenda back before its session.
  • Before these apps used tools (live, 23 October), the recruiter ran every stage once, in order, and the lecture spoke its three slides with no user input. What went wrong followed from one rule: a step does not move until the user has heard a turn written under it. A Q&A step that said "if they have none, start the quiz" had the model invent a quiz question. The training app has since made the quiz one step run by tools, so the page owns the order and the score.
  • The last step stays in force: the idle check-in said the farewell again 19 s after it ended.
  • The check-in and the persona are the avatar's, as in the mini-apps.
